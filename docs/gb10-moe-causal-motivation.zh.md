**先纠正研究顺序。**

上一版把基线验收、性能画像、动机实验和方案消融放在同一张清单中，而且部分动机实验已经要求实现“我们的调度器”。这样会形成循环：先选一个复杂方案，再用实验解释为什么需要它。

这版只保留三条因果链：

| 已有方法的直接组合 | 组合后可能出现的问题 | 动机实验 | 若成立，新增的设计变量 |
|---|---|---|---|
| SSD-LLaMA 式并发读取 + ProMoE 式预测优先级/分块 | 软件队列可以优先需求，已提交的多个预测读却仍占设备服务；小块也可能被深队列抵消 | E1：需求优先级是否传递到了真实 SSD 服务？ | 同时控制投机读取的块大小与未完成字节/提交深度 |
| SeqMoE 式长距离预测与槽位保护 + SSD 缓存 | 为隐藏更长读取而提前预约槽，受保护预测对象排挤更近的真实需求 | E2：同一预测集合，较早预约空间是否导致额外缺失？ | 预测产生、槽位预约、实际读取三个时刻分离；按空间机会成本决定开始时刻 |
| ZipMoE 式压缩缓存 + 提前预取 | 提前解压使远期对象过早膨胀；延后解压又可能不能按期供给 GPU | E3：数据到达和可计算就绪是否需要不同的提前量？ | 分别决定压缩数据读取与完整权重物化时刻，并共同预算其内存 |

E1/E2 是近期必做主线；E3 是有条件扩展。CPU 专家计算不占一个独立动机章节：只有成本证据表明值得，才加入后续动作集合。无需为了覆盖所有硬件模块而凑创新点。

**文献事实与推断边界。**

- SSD-LLaMA 将专家打包并并发读取，使用有限 staging/cache，完成后继续传输；其主流水线不进行投机读取。因此“加入预测后设备队列如何影响需求”是组合问题，不是其自身实验已经证明的缺陷。[SSD-LLaMA §4.1](https://arxiv.org/html/2609.18110v1)
- ProMoE 已通过分块和真实路由揭示后的高优先级处理缓解不可中途抢占的传输。因此 E1 必须比较调优后的固定分块，不能只打败 FIFO。[ProMoE §4](https://arxiv.org/html/2410.22134v1)
- SeqMoE 已有带宽估计、截止期调度、需求到来时暂停新预测提交，以及受保护的 Fetch/Compute 槽；其论文将预测完成对象保护到目标层处理。E2 研究这些机制迁移到 SSD 后的容量代价，不能声称原方法未考虑缓存或需求优先级。[SeqMoE §6—8](https://arxiv.org/html/2609.12978v1)
- ZipMoE 已有多种压缩状态、缓存池规划与按状态构建的重建任务图。E3 的候选增量是跨层预测条件下读入与物化时机的联合选择，不是压缩缓存或任务图本身。[ZipMoE §3](https://arxiv.org/html/2601.21198v2)
- 工程项目 S-MoE 的文档也描述了投机读取的带宽竞争和在途读取阻塞。因此“SSD 预取可能变慢”本身已有先例；这里需要证明本机规律及具体策略的增量。[S-MoE 开发者文档](https://docs.s-moe.com/v1/internals/streamer.html)

以上都是适用条件与组合风险。没有在 GB10 上完成相应测量前，统一使用“可能”“待检验”，不写“现有方法必然失败”。

**共同准备只做一次，不作为论文创新。**

固定模型、精度、Top-K、GPU 计算路径、自然 token 序列、读取布局与总物理内存预算。当前 Qwen3-30B-A3B BF16 的逻辑专家为 9 MiB，三矩阵各 3 MiB；这些数字来自模型形状。模型能在本机驻留，实验须标明是受控预算并加入全驻留参考。GB10 的 CPU/GPU 共用物理内存，所有真实副本和临时缓冲统一计数。[NVIDIA 硬件说明](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)

开发用 12 个固定请求：问答、代码、数学、长文本各 3 个，约 256 prompt tokens、128 个固定自然生成 tokens。各处理使用相同输入序列与 chat template。先在这些请求上诊断机制，再用来源分离的请求确认；诊断 trace 的不同回放不是独立用户样本。

准备项目：真实路由、预测候选的产生时刻、实际 I/O 区间、槽位状态、复制及消费者完成时间。当前分支已经出现 `moe_trace`、`async_demand` 和 M0 验收脚本；应复用已有实现，只补缺失字段，不按旧方案假定从零开始。是否通过 M0 以实际验收产物为准，本次未重新审计其结果。

总预算不能只限制专家缓存：读取目标、保留权重、复制源、计算目标、KV、预测器和工作区均计入；共享映射不重复计数。固定其他开销后，E2 开发先取剩余专家相关预算 4/8 GiB。E1 的隔离微基准只用固定缓冲池，避免缓存淘汰混入队列归因。

**E1：并发 SSD 读取与需求优先级是否冲突。**

待检验命题：在有真实预测流量时，调高并发虽然提高总读取吞吐，但已提交的预测请求可能使新揭示的真实需求等待更久；仅调整尚未提交的软件队列，未必能消除这一影响。

机制：在普通 pread/io_uring 路径上，不能假定取消请求必定能立即中断设备正在服务的读。ProMoE 的分块减少单次不可抢占传输，却不直接保证多请求 NVMe 队列中的真实需求延迟。这里必须测实际完成时间，不能用“所有在途字节/B”冒充严格阻塞下界，SSD 内部可能并行或重排。

第一步做不依赖模型前向的真实 I/O 回放。真实需求的到达时刻与文件偏移来自固定 trace；预测候选及产生时刻也固定。四种处理如下：

| 处理 | 行为 | 用途 |
|---|---|---|
| I0 | 无预测，只服务真实需求 | 需求延迟参照；不要求它读同样总字节 |
| I1 | 整专家读取，软件需求优先 | 直接结合并发流水线与预取 |
| I2 | 固定分块，软件需求优先 | 强已有机制；扫固定块大小和深度 |
| I3 | 与 I2 相同，但需求到来前已提交预测量受固定上限约束 | 因果干预，观察改变在途量是否能恢复需求延迟 |

投机块大小先取 1/3/9 MiB，提交深度取 1/4/8；物理块都满足实际 direct-I/O 对齐。9 MiB 完整专家在原 GGUF 中未必连续：可对相同专家生成统一的临时打包副本，所有处理使用同一副本，再只改变读取切分。不得让“换了磁盘布局”和“换了分块策略”同时发生。

在 I1/I2/I3 的机制回放中固定要读取的对象，结束时 drain 全部任务，使总服务字节相同；改变的只有顺序与已提交数量。需求与相同预测读相遇时加入已有任务，不重复读。流量额外开销要在之后在线实验中如实计入。

至少记录：需求入队→提交、提交→完成、总需求响应时间、需求到来时未完成投机字节、所有流量吞吐。操作系统 direct 请求尺寸也不等于物理 NAND 读量；块设备读量可作为补充观测。

主图两张：①横轴未完成投机字节，纵轴需求 p50/p95 响应时间；②横轴总有效吞吐，纵轴需求延迟，不同固定块/深度画散点。然后仅挑两组机制差异明显的配置做真实前向，确认需求响应的变化是否影响 TPOT。

成立所需证据：I2 的最佳固定设置仍存在吞吐与需求响应的冲突；降低已提交投机量能在同样工作下恢复需求响应；这项改变在实际前向中减少暴露等待。单纯看到 I1 慢于 I0 不够，因为那可能只是多读了无用数据。

结果对应设计：

- 若软件优先级已足够：使用现成优先队列，结束这一创新方向。
- 若固定分块/深度就能稳定解决：作为公共工程基线，不包装成算法创新。
- 若最佳分块与提交深度随真实需求密度/剩余提前量变化，并且最强固定配置仍明显折中：设计“根据到期裕量和未完成投机字节共同控制块大小与提交深度”。在线只在少量测得配置中选取，无须先引入完整滚动搜索。

候选新增贡献需要在冻结确认集上超过开发集选出的最佳固定配置，以及按需求暂停提交的强基线。回放中每段选择最优配置的 oracle 只用于估计空间，不作可部署算法。

**E2：延长预取窗口与保护缓存是否冲突。**

待检验命题：更长的 SSD 准备时间促使系统更早开始读取；如果从远期预测生成/提交起保护槽位，就可能牺牲当前更有用的驻留对象。提前量增加与缓存有效容量下降可能同时发生。

这里必须检查具体内存压力。48 层 × Top-8 × 9 MiB = 3.375 GiB，是每层都预备 8 个完整专家时的负载量级；它不是必然同时占用的测量值。预算充足或短窗口下，这个问题可能并不显著。

先锁定 E1 选出的一个读取配置，避免一边变窗口一边变并发。预测候选统一在相同可获得时刻产生；例如基于上一 token 的全层候选，所有策略都只能从同一产生时刻以后采取动作。真实未来只用于诊断 oracle，不提前泄露给在线方法。

三种处理使用同一候选集合、概率、预算、已有淘汰规则和真实访问：

| 处理 | 唯一干预 | 意义 |
|---|---|---|
| R0 | 不预取；保留同一缓存规则 | 测额外缺失相对谁产生 |
| R1 | 尽早预约并读入，保护到目标层 | 长距离预取与保护槽位的直接组合 |
| R2 | 先保留候选描述，到固定的目标前 d 层才预约并读取 | 隔离“何时占空间”，不实现新的淘汰算法 |

固定提前距离 d 先扫 2/8/24/48 层，预算 4/8 GiB。不是所有层都有全部提前距离，按实际可用窗口分层报告；不足 d 的对象从最早合法时刻处理。R2 的 d 在开发集选取，确认集不得按请求事后挑最优。

采集三段占用：已预约未就绪、就绪未使用、使用后保留。记录因预测预约而淘汰的对象及其后续真实再请求；用完整事件回放确认它是否造成额外读取，不能把每次淘汰都记成损失。配对回放还要统计双方反向独有的缺失，报告净变化。

隔离过程分两步：先固定路由事件逻辑顺序与服务模型做容量因果回放，观察额外缺失；再将选出的固定延后策略放入真实前向，计入缓存变化导致的全部补读和实际时间变化。不能为保持“相同字节”而隐瞒补读。

主图三张：①提前距离—就绪未用容量/时间；②提前距离—净额外需求读取；③提前距离—迟到等待与 TPOT。只有这条链在配对干预中成立，才能把性能变化归因于过早占位。

结果对应设计：

- 只因预测错误增加读取，容量占位影响很小：改进或收缩预测，不提出驻留时段机制。
- 一个固定 d 就足够：采用固定延后，归为参数调优。
- 大提前量补读多、小提前量迟到多，而且最佳 d 随当前空闲空间和近未来需求变化：设计“预测先登记，按截止期和受害对象机会成本决定槽位预约/读取时刻”。

初版规则可以十分具体：预测器输出保持不变；在预计读取完成可以赶上消费者的区间内，优先保留当前有价值对象；空间不足且预计被挤出对象的补读成本高于预取收益时，推迟或拒绝该预测。正在读、复制或计算的对象始终硬保护；完成后仅被预测需要的对象可重新评价，但不能破坏现有异步使用。

E2 的创新候选是读取时机与空间机会成本联动。缓存保护、动态缓存分数、普通预测准入已有先例，不能泛化声称首创。[SpecMD](https://arxiv.org/html/2602.03921)

**E3：压缩缓存与提前就绪是否冲突。**

这是独立的可选扩展，E1/E2 不依赖其成功。先测本地权重实际压缩率和解码时间；若压缩率不理想或成本过高，不进入完整 E3。

待检验命题：把“预测到的专家提前准备成可计算 BF16”直接加到压缩缓存，会让远期对象过早从压缩态膨胀到完整态。保留压缩态可以节约空间，但又增加使用前的解码工作。是否读取与是否立刻物化，不应默认绑定。

最小原型：从固定的若干层抽取专家，采用现成无损 codec，校验解码后逐字节一致；不训练模型、不改 router。首先做真实读盘＋解码＋既有 GPU 消费路径的重放，只有存在收益空间才构建全模型压缩文件。普通完整张量压缩原型只能证明机制，不能称为 ZipMoE 完整复现。

使用五种处理：

| 处理 | 行为 |
|---|---|
| C0 | 原始 BF16，按需读取 |
| C1 | 原始 BF16，固定预测预取 |
| C2 | 压缩存储/缓存，需求揭示后解码 |
| C3 | 同一压缩布局与候选，预测读取完成立即解码 |
| C4 | 与 C3 相同，压缩数据按原时刻读取，仅把解码延后到固定的消费前裕量 |

C3/C4 是归因关键：读同样压缩字节，变更的是物化时刻。比较 C0—C3 只能显示组合表现，不能用“组合加速小于两个单项加速相加”证明冲突，因为两者可能本来就消除重叠的等待。

记录压缩字节驻留、完整权重驻留、解码峰值、复制/目标缓冲、被挤出对象、解码未用的字节、解码导致的等待以及 GPU 消费时间。压缩源和解码目标同时存在时两者均计数；物化还需要额外计算目标时也计入。不得只统计稳定缓存而遗漏转换峰值。

主图：压缩数据准备和 GPU 可消费准备之间的时间差；完整态占用随时间变化；解码提前量—额外补读/解码迟到/TPOT。

结果对应设计：

- C3/C4 没有可测差异：立即物化即可，不加入额外状态控制。
- 延后物化减少内存压力，却增加可观的解码迟到，且最优时机随余量变化：设计分阶段预取，分别决定读压缩数据与物化完整权重的时机。
- GPU 减速主要由重建并发造成，内存占位不主导：另做固定内存占用的串行/并发对照；只有确认因果后才研究重建并发控制，不能用“统一内存”代替证据。

可实现规则：热专家保留完整态以避免反复解码；远期候选先保留压缩态；当预测消费者时间减去当前时间接近实测解码＋复制/准备服务时间及余量时，再预约完整态空间并物化。转换时必须检查总峰值预算，真实需求始终可前进。阈值来自开发测量，不预先规定一个通用毫秒数。

这一增量须与“ZipMoE 式多状态缓存＋固定提前量预取/物化”比较；不能把引入 compressed/full 两种状态本身写成创新。

**把实验结果直接翻译成方案，而不是在实验前锁定算法。**

| 结果组合 | 合适的方案范围 | 可以主张的候选贡献 |
|---|---|---|
| E1 成立，E2 不成立 | 动态读取粒度/提交额度，缓存采用已有方法 | SSD 需求服务约束下的投机读取控制；须超越最强固定分块/深度 |
| E1 不成立，E2 成立 | 固定 I/O 配置，联合准入与开始时刻 | 预测窗口与受保护容量之间的机会成本决策 |
| E1/E2 都成立 | I/O 提交额度与内存占位额度共同控制 | 同一预测任务需同时满足设备服务与空间时段约束，并验证联合优于独立控制 |
| E2/E3 都成立 | 压缩数据提前读，完整权重接近使用再物化 | 在表示大小、准备时间与误预测成本之间决定状态转换时刻 |
| E1/E2 都不成立 | 保留简单强基线，重新选择研究问题 | 不把异步实现和参数调优包装为上述算法创新 |

当 E1/E2 都成立，还需一个桥接实验：无控制、仅 I/O 控制、仅驻留控制、两者同时控制四组，使用同一预测器、候选及总预算。这是方案验证，不是前面的动机实验。联合收益可能非加性；看实际完成时间与对应队列/容量机制，不用加速比相加判断。

建议主方案暂命名为“面向统一内存 MoE 卸载的投机读取与驻留协同控制”。先让 E1/E2 决定其是否成立；E3 成立后再扩展为压缩表示下的分阶段准备。无需预先绑定某个 MPC、强化学习或复杂搜索算法。

**CPU 辅助计算放在哪里。**

CPU 是资源选择问题，不必另起一条泛化动机。在未压缩主线中优先用于 I/O 与管理；启用 E3 后，还可能承担解码。只有在这些任务并存时，实测 CPU 专家计算仍能降低整个层完成时间，才将其加入。要比较全 GPU、CPU 只解码、CPU 解码＋专家计算，包含对解码吞吐、I/O 提交和 GPU 的影响。不能仅凭单独 GEMV 测时就决定分担比例。

**实施顺序与最小交付。**

1. 复用当前验收与 trace，列出缺失字段；不重做已经通过的路径检查，也不把验收算动机。
2. E1 先做固定缓冲的真实 I/O 回放，交付两张图、处理参数和可重放 manifest。
3. E2 用同一批真实路由做容量回放，交付三张图，再将有解释力的固定干预放入前向验证。
4. 根据结果表选择方案；到这一步才实现动态控制器。
5. 压缩率/解码微基准支持时再做 E3；最后才开展跨模型、确认集、质量检查和模块消融。

每个动机实验最终都填写同一页结论：原方法的具体机制；迁移/组合改变了什么；控制变量；症状；去掉该原因后的恢复情况；剩余优化空间；对应新增决策变量；已有工作的重叠边界。少一项，就不能直接把它升级为论文创新点。
