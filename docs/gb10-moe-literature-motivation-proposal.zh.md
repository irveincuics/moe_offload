建议论文题目：**《面向统一内存平台的 MoE 专家卸载：基于计算依赖与驻留时间的联合调度》**。研究对象先限定为 GB10、单请求、原始路由与完整 Top-K、SSD 权重卸载；以 Qwen3-30B-A3B BF16 建立可验证原型。是否增加 CPU 专家计算，由实验决定。

**1. 文献核查后，必须撤回哪些宽泛的创新表述。**

不能再把“异步 I/O”“跨层专家预测”“预测置信度”“截止期调度”“缓存与预取协同”“CPU/GPU 混合计算”“统一内存上的任务图调度”单独称作创新。这些方向已有直接先例。下面覆盖与本项目最相关的主要路线，不代表穷尽所有论文；新近预印本与已发表工作都应纳入查重，但预印本的自报收益不能当作已复现结论。

最接近的比较对象是 **ZipMoE、SeqMoE、SSD-LLaMA、SpecMD**。前两个分别覆盖统一内存上的层内任务调度和预测驱动的跨步卸载；后两个提供强流水线和策略交互基线。只优于 LRU 或原始 mmap，不足以证明论文方案的增量价值。

不能把“论文未报告某实验”写成“该方法一定存在性能缺陷”。本文后续的不足分析，准确含义是：已有机制尚不能直接证明它在本设备、本预算、本执行约束下作出了最佳选择；我们提出可被实验推翻的假设。

**2. 先把本设备上的问题界定正确。**

GB10 使用 CPU/GPU 一致性统一内存，DGX Spark 标称 128 GB、273 GB/s 内存带宽。这是硬件标称值，不是专家读取的实测速度。[NVIDIA 硬件说明](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)

本地此前核查到 20 核 Arm CPU、约 121 GiB 可见内存和单块约 4 TB NVMe。Qwen3-30B-A3B BF16 文件为 61,089,832,960 字节；48 个 MoE 层、每层 128 专家、Top-8、hidden=2048、expert intermediate=768。由形状计算：

- 单矩阵专家切片：2048 × 768 × 2 B = 3 MiB。
- gate/up/down 三矩阵合计：9 MiB/专家；每层选中负载 72 MiB。
- 单个 decode token 若所有选中权重均缺失：48 × 8 × 9 MiB = 3.375 GiB。
- 全部路由专家权重：54 GiB。它本身能装入本机物理内存。

因此第一组实验应明确称为“**受控专家内存预算下的卸载实验**”。必须加入全驻留 GPU 参考；不得写成“30B 模型在本设备上无法驻留”。若论文要主张扩展模型容量，后续必须增加实际工作集超出可用内存的受支持模型，或有真实其他负载的共存场景；单纯限额不能代替该证据。

若每 token 的实际需求缺失比例为 m，暂不计浪费读取，需求负载为 3.375m GiB。SSD 有效带宽 B 下，长期平均每 token 的存储服务时间至少为 3.375m/B 秒。有限序列可提前读入，需把预热与额外读取计入。举例若实测 B=5 GiB/s，m=0.5，仅服务需求读取就需约 0.338 s/token；这只是算例。预取只能重叠这部分服务，不能消除流量。

总预算按唯一物理分配统计：非专家权重、KV、缓存、未完成读取的目标槽、复制源、计算工作区、预测器与必要元数据。共享映射计一次，真实复制计两次。现有全形状 CUDA 工作区不等于“只占当前选中的 72 MiB”，需单独实测。CPU/GPU 分配器数字不能简单视为两块独立容量相加。

**3. 核心研究假设要比“命中率不等于性能”更具体。**

建议检验以下机制链：

> 在有限统一物理内存中，一次跨层预取不仅消耗读取带宽，还提前占用一段容量；是否值得，取决于它是否缩短某个真实消费者的等待、占用期间挤掉了什么，以及并发期间改变了其他读取/计算的服务时间。

这一点作为常识也不是创新。候选研究贡献是：**在当前后端的真实依赖和生命周期约束下，建立能正确排列动作优劣的模型，并据此在线联合选择读取、延后、保留与淘汰。** 必须证明它优于“强预测器 + 已有缓存 + 已有截止期调度”的组合。

四个可否证假设：

| 假设 | 需要观察的证据 | 反证及后续处理 |
|---|---|---|
| H1：预期命中贡献不足以排序读取动作 | 固定预测输出与总读取预算，消费者完成时间排序比置信度/EDF 更好 | 排序结果与性能无区别：删除这一算法主张 |
| H2：预取开始时刻与驻留时段显著影响未来缺失 | 同样读取对象、同样总字节，延后部分读取可减少过早淘汰且不增加迟到 | 收益仅来自多给缓存：实验无效；占用时段无影响则无需复杂驻留规划 |
| H3：并发会显著改变成本模型，静态服务时间会选错动作 | 相同权重、内核与工作量，并发度变化导致动作收益排序反转 | 干扰落在测量噪声内：移除干扰控制，仅保留较简单的 I/O 模型 |
| H4：CPU 专家分担在某个真实区域有净收益 | 包含等待、同步、归并与 GPU 被拖慢成本后，总层延迟仍下降 | CPU 始终输：CPU 只做 I/O、预测和调度，不纳入专家计算主方案 |

特别是 H3 不能预设成立。ZipMoE 已测量其平台上的解压/I/O 干扰并判断影响较小；这提醒我们测量具体并发任务，而不是因为“共享内存”就推断带宽一定严重竞争。[ZipMoE §2.3](https://arxiv.org/html/2601.21198v2)

**4. 动机实验的共同协议。**

先做 12 个开发请求，覆盖问答、代码、数学、长文本各 3 个；每个 prompt 约 256 token，固定回放 128 个自然生成 token。原始内容、模板、token 序列、模型哈希、提交版本全部冻结。开发实验用于筛选假设，不报代表性总体结论。

确认集另选 48 个请求，每类 12 个，与开发集按原始题目/文档分组分离，避免同源改写进入两边。冻结主参数后再运行。用于压力测试的 2048-token prompt / 256-token generation 另取 12 个请求；不做所有参数的笛卡尔积。较长生成与更大样本根据开发阶段的方差和耗时追加。

同一策略对比走两条路径：①固定真实 token 的 teacher-forced 正常前向，便于因果比较；②真实生成确认行为与用户可见时间。只回放路由 ID 的模拟器用于选策略，不代替端到端结果。若采用 fused Top-K 算子，在该消费者完成前保留它需要的全部源/目标对象；逐专家串行访问的模拟器不能冒充这种语义。[回放语义研究](https://arxiv.org/html/2608.07911v4)

缓存有效负载容量先取 4/8/16/32 GiB，另计所有工作区并报告固定总预算；比较方法要满足同一总物理内存上限。主实验先用 8/16 GiB，只有筛选通过的方法再扩展。每个配对实验重复 3 次，交错/随机运行顺序；固定功耗模式，记录频率、温度和后台负载。操作系统页缓存状态、应用缓存状态分别描述，不能仅写 cold/warm。

主指标：请求级平均 TPOT、TTFT、每请求 token 延迟分位数；同时报告需求读取字节、全部读取字节、浪费率、设备读量、消费者暴露等待、峰值内存与调度开销。跨请求汇总采用请求级配对差值和 bootstrap 区间，不能把同请求的所有 token 当独立样本。小样本不强报 p99；失败/OOM/热降频与反向结果保留。

**M0：验证测量对象，避免在错误后端上讨论优化。**

目的：确认实际执行的是“SSD → 有限缓存 → GPU MoE”，并取得可信时间线。

操作：全驻留、现有 mmap、现有 V2、异步按需四种基线依次检查真实算子后端、选中专家数、显式读量、复制与 CUDA 完成事件。现有环境变量 `GGML_OP_OFFLOAD_MIN_BATCH=1` 仅作诊断；最终以后端日志为准。路径检查使用 verbose，正式测时关闭逐节点日志。

必须记录下列事件：request/eval/token/layer/projection、真实专家集合、预测产生、槽位预约、入队、实际提交、I/O 完成、复制提交/完成、消费者开始/结束、淘汰。host 使用单调时钟；device 用 CUDA event 或分析器相关时间轴。对跨时钟事件先做关联，不能直接相减。为减少扰动，完整诊断与轻量测时分开，并测日志开销。

特别修正：现有 worker 的 I/O 时间之和不是 GPU 暴露等待；buffered pread 读到的数据可能来自页缓存；模型元数据里出现 GB10 不代表专家算子在 GPU 上运行。`llama-bench` 的随机 token 只适合性能路径检查，不适合证明自然语言路由局部性。

验收：权重/结果检查通过；trace 中每次已选专家缺失有唯一读取或加入已在途任务；消费者不早于数据可用；所有源槽在读、复制期间不复用。M0 不通过，暂停后续性能结论。

**M1：测“值得优化的空间”与物理带宽边界。**

固定：模型、路由 trace、计算路径、容量。比较 LRU、LFU、Least-Stale 类策略、离线未来访问信息辅助策略，以及全驻留参考。

先做三种明确分开的离线参照：

1. 等尺寸、无 pin、标准 mandatory-admission paging 下的 Belady MIN：仅作为该放松问题的最少缺失参照。
2. 遵守当前 Top-K pin 与在途槽约束的未来信息启发式：可执行的未来辅助参照，不能称为已证明最优。
3. 已知未来路由但仍受真实 SSD、缓冲和执行约束的调度回放；少量固定 trace 可将已知未来路由输入运行时做不可部署的上限诊断。

不把“零 I/O 成本”与“准确预测但仍需读盘”混为同一 oracle。不直接将静态命中率换算成 tokens/s。

产图：容量—总读取字节/token；容量—TPOT；每 token 服务需求与可重叠窗口；真实活跃专家并集/缓存容量的分布。若未来信息辅助也几乎不比强在线基线好，则复杂缓存/预测研究价值有限。若读量下界已经超出目标吞吐的可供带宽，进一步预测无法解决，应转向降低每 token 流量或修订目标。

**M2：在相同预测输出下，预取效用到底损失在哪里。**

预测器先固定为“上一 token 同层专家 + 层间相关性”这一已有技术路线，或一个已有学习预测器；不在比较调度器时换预测器。把每个预测去重后按以下互斥状态分类：已驻留、已在途、新读取且按期被用、新读取但迟到、新读取后被提前淘汰、新读取且在声明窗口内未用、因预算未读取。未完成试验窗口的对象标记为 censored，不能算浪费。

分别报告预测 precision/recall、面向缺失集合的 recall、按期可用率、实际减少的暴露等待和浪费字节；预测到已驻留对象不刷新需求 recency/frequency，另设刷新版本作对照。Routide 已报告过这种探测污染，故这里是复现实验和控制条件。[Routide §3.3、§5.2](https://arxiv.org/html/2609.29032)

比较：置信度排序、EDF、SeqMoE 风格的置信度/截止期可行集合、拟提出的消费者完成时间排序。共同输入候选、预测概率、读取上限、总容量和执行内核。开发阶段先离线，再挑选有差异的固定请求做在线验证。

产图：相同预测质量下的 TPOT—总读取字节 Pareto 曲线；预取去向堆积图；预测分数与实测延迟收益的排序一致性。若只是“预取更多所以更快”，不能归因于更好的调度。

**M3：拆开“缓存放什么”与“从什么时候开始占用”。**

问题：长提前量是否让尚未使用的预测权重排挤当前/近未来真实需求？

干预：固定一个请求的预测对象集合与每对象读取次数，分别尽早读取、按预计消费时刻倒推读取、按容量时段约束读取。初步回放固定读取集合；真实运行中若引起补读，补读字节必须纳入差异，不能继续声称流量相同。

定义对象占用面积 A_j = 实际分配字节 ×（释放时刻 − 槽位预约时刻），单位 MiB·ms。面积用于衡量压力，**不能替代任意时刻容量不超限的硬约束**。分别统计在途、就绪未用、真实使用后保留的面积，以及读入后首次使用前被淘汰比例。

二维小扫：容量 4/8/16 GiB，最大预测在途数 1/2/4，提前窗口由实测服务时间决定。缓存与预取的槽位共用同一预算，不能给预取额外免费内存。当前确定需求保留可前进的额度，避免所有空间被预测任务占住。

产图：内存状态随时间堆积图；驻留面积—额外补读—TPOT；同一请求的配对时间线。支持 H2 的关键证据是：联合选择保留/延后动作，在相同总预算下减少补读或消费者等待，而非只换一个缓存分数。

**M4：并发成本模型是否真有必要。**

三类固定工作：A=GPU 原 MoE/attention 片段；B=真实对齐 SSD 读取并经现有复制路径送到工作区；C=CPU 计算或 CPU 预处理。先测 A/B/C 单独，再测 A+B、A+C、A+B+C。权重布局、总字节、计算量相同；预热状态分别控制。

读取并发取 1/2/4/8；CPU 线程先取 0/2/4/8，分别固定到核组后再做必要扩展。Arm 大小核差异单独记录，不把逻辑核编号当作性能等级。先用局部微基准筛选，避免完整笛卡尔积。

记录 GPU kernel 延长比例、设备读吞吐和 p50/p95 服务时间、复制时间、CPU 完成时间、层完成时间与功耗模式。若可用计数器，补充 DRAM 流量；否则明确只有时延证据，不能声称测得 DRAM 饱和率。

对比成本预测：独立测量常数、在线平均服务时间、按队列深度/并发状态条件化的模型。比较预测误差，更要比较“哪种动作更快”的排序与在线 regret。只有条件模型能稳定改正决策且净收益超过其开销，才保留 H3 对应机制。

**M5：CPU 到底应该辅助什么。**

对本地真实 2048×768 专家三投影，测试 CPU 1/2/4/8 线程和 GPU；小批 token 行数 1/4/16/64，专家数 1/2/4/8。先测单设备，再测可行的 CPU/GPU 分工。使用当前 Arm 可用内核，x86 AMX 数字不能用于预测本机速度。

比较全 GPU、固定 CPU 比例、只用独立延迟选择分工、使用并发实测成本选择分工。包含 CPU 输入准备、两边等待、输出归并，以及 CPU 任务使 I/O/调度变慢的代价。SSD 未读入的专家无论去哪个设备都要读，不能把“交给 CPU”误计为免读盘。

启用 CPU 专家分担的条件是估计并实测：max(并发下 GPU 分支完成时刻, 并发下 CPU 分支完成时刻) + 归并成本，小于全 GPU 路径完成时刻，且差异超过噪声。若后端暂不支持逐专家跨设备并行，这一步先作为微基准上限判断；不要先承诺实现再找理由。

**M6：组合收益、分布变化与开销验证。**

固定参数在确认集运行：基础异步按需、强缓存+截止期预取、加入驻留时段决策、加入条件服务模型、完整方案。另将预测器替换为另一种已有方法，检验收益是否依赖某个弱预测器。

分布变化采用不同类型请求交替到达，明确请求间缓存是否保留、预测历史是否重置。单独做冷启动和稳态；不把测试未来路由放入在线预测状态。报告平均值、请求级离散程度、最坏退化、调度 CPU 占用、额外元数据与日志开销。

确认集的成功标准在开发后冻结：至少两个相邻容量点，相对最强同约束基线取得超过测量噪声和控制开销的净收益；去掉关键模块后收益按预期下降。可设“TPOT 降低 10%”为项目继续投入的工程门槛，但它不是先验科学结论，也不是承诺结果。不得根据确认集结果反复改阈值。

**5. 由这些动机实验导出的完整方案。**

方案不额外训练大预测器、不改 router、不丢专家、不降低原权重精度。预测器提供候选及概率；研究主体是这些候选进入资源系统的时机和与真实需求的关系。

运行时维护四部分状态：

- 实际计算 DAG：router、gate/up、激活、down、归并与层间依赖，以当前 CUDA graph split 为准。消费者可能是一个投影上的 Top-K fused 算子，不能虚构已存在逐专家异步执行能力。
- 读取状态：对象位置与尺寸、排队/已提交/已完成、直接 I/O 或回退路径、队列深度和服务时间分布。
- 内存状态：物理槽、复制源与计算目标、硬 pin 原因、预测保留截止时刻及对象代次。
- 预测状态：只含当前可取得的历史；预测概率、预计使用窗口和校准误差。真实需求记账与预测探测分开。

以 `(layer, expert, projection)` 为物理对象，9 MiB 逻辑专家为关联组。相同路由下 gate/up/down 是相关需求，但原内核的消费者不同；是否一次读完三矩阵由真实 I/O 服务曲线与依赖决定。初版默认沿用三次矩阵读取，增加一次整专家打包读取作为公共基础优化对照，不将布局本身算创新。

**候选贡献 A：可用于决策的消费者完成时间模型。**

对某消费者 n，建立局部近似：

    start(n) = max(所有前驱完成时刻, 所需权重可用时刻, 执行资源可用时刻)
    finish(n) = start(n) + service(n | 队列与并发状态)

service 来自微基准表和在线滑动更新，带不确定度；对有限预测场景计算未来窗口完成时间。若同一个 fused 消费者等待多个对象，提前一个非瓶颈对象可能没有立即收益；因此不能简单相加“每专家省下的 ms”。在分组动作有互补性时，同时评估一组对象，避免单对象贪心永远看不到收益。

该模型是近似调度模型，不宣称为底层 GPU/SSD 的精确模拟器。先以 M4 检验动作排序；若排序不准，不能直接上线复杂控制。

一个仅用于解释的简化反例：消费者同时等待 A、B 两个等大小对象，既定调度下分别在 2 ms、8 ms 就绪；预取 A 或 B 都增加一次命中。若提前准备 A，消费者仍在 8 ms 开始；若提前准备 B，消费者可在 2 ms 开始。两者命中数相同，收益分别为 0 和 6 ms。真实系统中预取还会改变队列与受害对象，因此必须重新评价整个局部计划；这些数字不是本机测量结果。这个反例解释目标函数差异，本身不构成新的理论发现。

**候选贡献 B：将读取开始与保留时段联合决定的滚动调度。**

每个对象 j 有预约开始 a_j、释放/再决策时刻 z_j、物理尺寸 s_j。每个计划必须满足所有事件时刻的容量约束：

    fixed_memory(t) + Σ_j s_j · I[a_j ≤ t < z_j] ≤ total_budget

复制源与目标若是两次分配，则作为两个区间；GPU 正在读的缓冲区使用不可撤销的硬 pin。尚未被真实需求确认的预测保留使用可撤销承诺：紧急需求到达后允许重新评价，但不能覆盖在途读/复制/计算缓冲。

对计划 P，优化未来窗口完成时间的期望，加上预测误差造成的尾部风险与控制成本；同时设置读取字节和在途数上限。尾部项先作为可选消融，不默认复杂模型一定更好。保留、淘汰、提前读、延后读和放弃预测均使用同一完成时间评价。

为避免窗口末尾清空缓存的短视，终端状态加入基于历史下一次使用分布的保留价值；通过加长窗口检验敏感性。在线不允许使用真实未来。离线未来辅助仅用于 M1。

具体可实现的初版求解器：

1. 当前确定需求先获得进度保证；去重并将相同在途预测任务升级为需求任务。
2. 从已有预测器获得未来层候选；先删除已驻留、已在途对象，但不更新真实使用频率。
3. 窗口先取 4/8/16 层，由实测读取时间与层执行时间选择；若短窗口无法覆盖读取，扩展到后续层/下一 token，或减少预取，不能强行使用一层提前量。
4. 最多保留 32 个单对象/关联组候选，考察“现在读取、延后、跳过”与必要的缓存受害者；采用宽度 4、深度 2 的有限搜索作为起点。
5. 对少量来自开发数据与历史的路由场景评价候选计划；场景应保留 Top-K 共激活结构，不能把每专家视为独立伯努利。先用 4 个场景，确认误差后再决定是否增大。
6. 用相同场景比较计划与不行动，只有净收益超过成本不确定度与决策开销才提交。搜索超时直接回退按需/已有截止期策略。
7. 每次只执行首批动作。I/O 完成、真实路由揭示、层推进时更新状态；不为每个 worker 中断重新跑全搜索。

以上候选数、宽度、深度是待剖析的工程起点，不是已经验证的最优参数。首先在 trace 上离线跑完整策略，再限制在线开销。开发目标是控制开销不超过基线 TPOT 的 1%；测不到这个水平就缩减搜索或使用离线策略表，不靠更复杂模型维持表面创新。

**候选贡献 C：按实测服务变化控制并发，CPU 计算是受条件约束的动作。**

慢速控制器每 32 个 token 或出现明显服务时间漂移时更新读取并发与 CPU 线程配置；快速调度器按真实路由事件选择任务。读取并发候选先为 1/2/4/8；只在开发阶段允许探索较差配置，正式测量计入初始化成本并保留保守回退。

只有 M4 支持干扰假设才使用条件成本；只有 M5 证明收益才把“此专家交给 CPU”加入动作集合。否则主方案是 GPU 完整计算，CPU 做预测、I/O 和管理。不能为了凑第三个创新点，把无收益的混合执行加入系统。

**7. 论文基线、消融与创新点的最终表述。**

主要基线至少包含：全驻留参考；当前 V2；统一强 I/O 上的 LRU/LFU；Least-Stale 类淘汰；同一预测器下的 EDF；同一预测器下的 SeqMoE 风格任务选择；离线未来辅助参照。资源允许时适配 ZipMoE/SSD-LLaMA 的公开实现；若只重现论文某个机制，明确标为“机制适配”，不能冒称原系统完整复现，更不能照搬论文图中数字作同机结果。

需要一组“增强已有方法”的困难基线：强缓存 + 条件服务时间 + 截止期预取，各部件分别优化但无时段联合搜索。只有完整方案还胜过这一组合，才能说明收益来自联合决策，而不只是给已有算法加入公平的带宽估计。

消融顺序：去掉时段约束→固定驻留；去掉消费者依赖→按独立专家得分；去掉条件成本→静态服务时间；去掉未来终端价值→纯短窗口；去掉关联组动作→单对象贪心；去掉预测→纯按需。每次保持相同总容量与原模型计算。

质量验证不因“不改模型”而省略：核查加载字节、实际 router Top-K、选中权重与参考前向；同设备同内核优先测试输出一致性。若变更算子/归并顺序，引入浮点差异，报告 logits 误差与真实生成结果，不轻率承诺逐 token 位级相同。近似专家/裁剪/改路由方法的比较独立报告质量与速度。

动机实验支持时，可写成以下两项主贡献和一项系统证据：

1. **问题与模型贡献**：刻画 SSD 支持的统一内存 MoE 中，真实消费者依赖、预测对象占用时段和并发服务时间对在线决策的影响，并证明哪些状态是必要的。
2. **算法贡献**：在原路由与固定物理内存预算下，联合决定跨层预测对象的读取时机及保留/淘汰，通过受限滚动搜索降低消费者等待与尾部退化。
3. **系统与验证贡献**：实现遵守 I/O/复制/计算生命周期的运行时，以真实 NVMe、自然 token、同预算强基线和消融验证净收益及适用范围。

第三项不能仅凭“实现了系统”自动算独立算法创新。两项扎实、可解释、超过最接近工作的贡献，比强凑四项通用优化更适合论文。

若 H1/H2 不成立，或者收益只能来自异步流水线，应如实把成果定位为工程优化，不继续包装缓存算法创新；若 I/O 下界主导，则另立“降低每 token 流量”的研究问题，重新对比 ZipMoE 与 BigMoMo 后设计压缩/多 token 复用实验。不能将尚未验证的备选方向写为已经成立的贡献。

本方案现在达到的是：文献边界可核查、假设可否证、实验可以执行、实现入口具体。是否足够构成最终毕业论文的创新，取决于动机证据、强基线比较和实际实现结果；目前最优先完成 M0、M1、M2、M3，再决定是否投入完整控制器。
