本文整理 NVIDIA GB10 统一内存设备上的 MoE SSD 卸载优化方案，依据截至 2026-09-23 查阅的本地代码、已有日志和公开论文。当前未找到用户提到的开题报告，因此研究目标与报告章节的对应关系尚待补充。下述方案是待实验验证的设计建议，不是已实现功能或实测加速结论。

**1. 建议的研究主线是：在统一物理内存预算下，联合优化专家驻留、SSD 读取、预取时机和执行位置，最小化每个 token 的关键路径等待。**

优先顺序建议为：核验执行路径与基准；减少不必要读取和拷贝；设计分层缓存；实现带宽与截止时间约束的预取；最后评估 CPU 专家计算。量化作为独立实验轴，与保持 BF16 不变的系统优化分开报告。

当前模型权重本身能够放入本机物理内存。如果目标只是加速当前 Qwen3-30B-A3B 的单实例短上下文推理，应先建立全权重驻留、GPU 计算的基准。SSD 卸载的研究价值主要体现在受限内存预算、更大模型、多实例或长上下文场景下，改善速度与内存占用的折中。

**3. 首先修正实验解释，避免优化了没有运行的路径。**

已有 [sched-debug.log](/home/cuichengshang/moe_ssd/test/ssd_v2_analysis/sched-debug.log:1909) 把专家 `MUL_MAT_ID` 标为 CPU；同文件末尾缓存 hits、misses、disk 和 backend_copy 全为零。这份日志对应的运行没有验证目标中的 GPU 专家读取通路，不能据此比较 V2 缓存优劣。其他名为 `gpu` 的 JSON 文件仅凭文件名与 `n_gpu_layers=999` 也不能确认算子最终落在 GPU。

当前 CUDA 后端的机会性算子卸载判断存在默认 batch 阈值 32，`MUL_MAT_ID` 使用 `op->ne[2]` 判断；这是单 token 专家留在 CPU 的一个明确排查入口。可把 `GGML_OP_OFFLOAD_MIN_BATCH=1` 作为诊断对照，但必须重新查看算子分配和统计，不能把该环境变量当作已经验证的修复。[卸载判断](/home/cuichengshang/moe_offload/llama.cpp/ggml/src/ggml-cuda/ggml-cuda.cu:5536)、[默认阈值](/home/cuichengshang/moe_offload/llama.cpp/ggml/src/ggml-cuda/ggml-cuda.cu:5710)

现有多份结果使用 `n_gen=1`，只适合路径检查与短调用开销观察。当前 [test_gen](/home/cuichengshang/moe_offload/llama.cpp/tools/llama-bench/llama-bench.cpp:2237) 在每步喂入随机 token，并非真实文本自回归生成。它可以做内核基准，但不能独立证明时间局部性、语义预取或请求级专家缓存效果。需要补充真实 prompt 与生成轨迹，并在比较系统策略时重放相同 token 序列。

还有两处统计口径需要区分：代码中的 `io` 是多个 worker 耗时的累计值，不能直接当作端到端阻塞时间；`disk` 记录显式读取请求的字节数，buffered pread 可能命中 page cache，因此不能总被解释为 NVMe 实际物理读取量。应另采集块设备读取量与需求线程等待时间。

**4. 用容量和带宽模型确定优化上限。**

按本地 BF16 配置计算，一个专家的三个矩阵大小合计：

`S_expert = 3 × 2048 × 768 × 2 bytes = 9 MiB`。

每层 Top-8 的逻辑权重需求为 72 MiB；48 层每 token 需要访问约 3456 MiB，即 3.375 GiB 的专家权重。全部 routed expert 权重为 54 GiB，8 GiB 应用缓存约覆盖其容量的 14.8%；实际命中率取决于访问分布，不能由容量比直接推断。

令 H 为不需要新增 SSD 读取即可复用的专家字节比例，则无额外错预取时，SSD 需求字节约为 `3.375 GiB × (1-H)`。在长序列稳态下：

`平均 token 时间 ≥ max(实际 SSD 总读取字节/token ÷ 有效 SSD 带宽, DRAM 流量/token ÷ 有效 DRAM 带宽, 有依赖的计算关键路径)`。

这是吞吐下界，各阶段依赖和同步会让真实时间更长。预取能隐藏部分等待，不能突破持续带宽上限；错误预取还会增加总读取字节。启动前已完成的预取需要计入冷启动或另外披露。

仅作数量级示例：假设实际 SSD 带宽为 6 GiB/s，H=0、80%、90% 时，仅专家 SSD 传输分别约需 562.5、112.5、56.3 ms/token。若希望达到 20 token/s，即便忽略其他开销，也需 H 至少约 91.1%。6 GiB/s 是示例假设，不是本机测量值。

同样假设下，一层 72 MiB 全冷读取约需 11.7 ms。因此只提前一层未必够用；需要根据真实计算窗口选择预取距离，并结合缓存和量化降低带宽需求。

**5. I/O 优化：先减少拷贝与等待，再判断是否需要替换 I/O API。**

| 建议 | 具体设计 | 必须验证的条件 |
|---|---|---|
| 三种 I/O 基准 | 同一访问轨迹下比较 mmap/page cache、buffered pread、O_DIRECT + 应用缓存 | 总物理内存预算相同，冷热状态可解释；O_DIRECT 不保证更快 |
| 对齐槽位与复用 | 预分配对齐的缓存槽位，允许时直接读入最终槽位，复用 worker buffer | 消除当前每次 miss 的 `posix_memalign/free` 与 bounce-buffer memcpy；不提前覆盖仍被 GPU 使用的槽位 |
| 专家打包 sidecar | 按 `(layer, expert)` 建索引，每条记录保存 `[gate][up][down]`，记录 dtype、形状、长度、校验与模型身份 | 不改原 GGUF；按目标文件系统实际 direct-I/O 要求对齐，4 KiB 可作候选布局 |
| 控制打包粒度 | 比较三个矩阵独立读、gate+up 合读、完整专家 9 MiB 合读 | 当前 3 MiB 已是大请求；合并不能假定获得三倍带宽，完整读还可能延迟 gate/up 提前计算 |
| 多请求并发 | 扫描 worker=1/2/4/8 与队列深度，记录有效 GiB/s、p95 延迟和 CPU 使用率 | 只增加并发未必提高 NVMe 吞吐，还可能延长需求请求等待 |
| io_uring 对照 | 批量提交、完成队列、持久缓冲区，和同队列深度的 pread 线程池比较 | 仅在提交/唤醒/线程调度成为瓶颈时提升优先级；不预设 API 替换本身会显著提速 |
| 优先级与分块 | 为需求读取预留队列额度，预测读取低优先级提交；大预测读取按可测粒度分块 | 已提交到设备的读不一定能即时抢占，取消通常先作用于尚未提交请求 |

整专家连续布局的动机可参考 LLM in a flash 的联合布局与时间复用思想，但该论文的神经元稀疏化机制不能直接等同于 Qwen3 的专家访问。[LLM in a flash](https://arxiv.org/abs/2312.11514)

同一层路由一旦给出 Top-K，gate/up/down 的选择已知。可以立即提交三者的确定性读取，让 down 权重读取与 gate/up 计算重叠。这是低风险的第一种预取，不依赖跨层预测准确率。

**6. 统一内存优化：让命中专家尽量不再复制。**

当前缓存命中仍经 `ggml_backend_tensor_set_async` 写入 CUDA 临时输入；统一内存硬件并不会自动删除这条软件复制。可依次做三个版本：保留复制但复用槽位与事件；建立紧凑专家槽位并重映射 ID；最后让 CUDA kernel 通过稳定的专家指针表直接访问已驻留槽位。

零拷贝试验前需查询 `pageableMemoryAccess`、`pageableMemoryAccessUsesHostPageTables` 等运行时属性，验证选定分配类型、内核与驱动组合。统一地址空间、统一物理内存、`cudaMallocManaged` 是相关但不同的概念。仅设置 `GGML_CUDA_ENABLE_UNIFIED_MEMORY` 不会自动实现专家缓存零拷贝。[CUDA 系统内存文档](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html)

缓存槽位应有加载中、就绪、使用中和可回收状态，使用 event/引用计数保证生命周期。淘汰只等待候选槽位的最后一次使用结束，逐步替代当前容量不足时的整后端同步。固定地址池也便于后续探索 CUDA Graph，但动态 ID、指针与图更新成本必须一起验证。

对零拷贝需分别测完全命中、受限容量与冷读场景。它可能减少 DRAM 流量和容量重复，却也可能增加地址转换或不规则访存成本；只给真实收益，不按删除的 memcpy 字节数直接推算加速比。

**7. 缓存策略：优化“省掉的等待时间”，而不只追求访问命中率。**

第一步把逻辑管理单元改为 `(layer, expert)`，三个矩阵共享热度、入场与生命周期元数据，同时允许不同矩阵按依赖分别 ready。这样不必强制等完整 9 MiB 到达后才开始计算。

替换策略按以下顺序试验：LRU 基线；带老化的 LFU 或 2Q；分层配额加全局共享空间；最后加入预取感知的成本策略。逐层、逐 token 的扫描可能削弱全局 LRU 对跨 token 复用的保护，但是否严重需要真实轨迹证明。

可以采用以下待验证的评分，而不是直接沿用 router 权重当热度：

`保留价值 = P(在评估窗口内再次使用) × 预计可避免的关键路径等待 / 占用字节`。

概率由近期频率、请求历史、token 间复用及预测器输出估计；等待成本要考虑该层是否还有预取窗口。窗口内多次复用时可改用预计复用次数。为每层保留最低额度，额外空间按增加一份缓存能减少多少等待来分配。

分出“已被真实请求使用的保护区”和“预测试用区”；错预取优先淘汰，预测访问不能自动获得真实命中的高优先级。预取区起始可试 5%/10%/20%，由浪费字节率和需求阻塞反馈调节，这些数值是扫描候选。

Fate 的浅层优先缓存提示了一个值得测量的方向：预测差、可隐藏窗口短的层可能更值得常驻。但不应固定认定 Qwen3 的前若干层一定最优；应测每层预测准确率、及时完成率、热度与缺失等待。[Fate](https://arxiv.org/html/2502.12224v2)

请求级热点和历史激活轨迹可参考 MoE-Infinity；本机要将其 GPU 缓存思路转为统一内存预算下的专家驻留策略。[MoE-Infinity](https://arxiv.org/abs/2401.14361)

总预算应覆盖非专家权重、KV、专家驻留、计算 workspace、I/O 缓冲和 OS 余量。buffered I/O 的 page cache 与应用副本也要计入同一物理预算；不能用 CUDA 占用下降证明整机内存下降，也不能把同一物理页的不同视图重复计数。

**8. 高层预取：由便宜的历史预测逐步升级到有截止时间的跨层预测。**

| 层次 | 候选策略 | 优势与限制 |
|---|---|---|
| 确定性 | 当前层 Top-K 已知后立即读取全部对应矩阵 | 无错预取，先验证 I/O 与 gate/up/down 计算重叠 |
| 时间历史 | 上一个 token 同层专家、短窗口出现频率 | 成本低；主题变化和真实路由分布可能使预测失效 |
| 请求历史 | 按当前请求的专家激活签名检索近似历史路径 | 适合复用请求特征；需控制检索成本和跨请求污染 |
| 跨层 gate | 用较早层的隐藏状态和目标层 gate 近似预测 Top-M | 无需修改正式路由；隐藏状态相似不保证 Top-K 相同 |
| attention 前预测 | 在同层 attention 前估计 MoE 专家 | 为当前层留出 attention 计算窗口；已有论文验证过 Qwen3-30B，仍需本机测量 |
| 轻量可训练预测器 | 由较早层特征预测未来多个层的专家概率 | 增大提前量，代价是训练、预测开销与分布泛化问题 |

跨层 gate 可参考 Fate；预测准确率与提前量联合评估可参考 ProMoE；同层 attention 前预测可参考 Pre-Attention Expert Prediction。Pre-gated MoE 是算法与系统协同设计，不能当作无需适配训练就能直接套到现有 Qwen3 权重上的开关。[ProMoE](https://arxiv.org/html/2410.22134v1)、[Pre-Attention Expert Prediction](https://arxiv.org/abs/2511.10676)、[Pre-gated MoE](https://arxiv.org/abs/2308.12066)

建议保留原始 router 的最终专家选择：预测只影响搬运；预测漏掉的真实专家仍按需读取并计算。这样读取预测错误影响性能，而不直接改变模型语义。近期 SpecPrefetch 也采用将搬运预测与正式路由分离的设计。[SpecPrefetch](https://arxiv.org/abs/2607.24787)

调度器为每个候选估算“需要时间”和“完成时间”。当 `队列等待 + 预计读取时间 + 准备时间 ≤ 剩余计算窗口` 且期望节省大于预测、读取浪费和缓存污染成本时，才优先预取。过期候选降级或取消尚未提交部分，需求请求始终保留提交额度。

初始扫描可用前瞻距离 1/2/4/8 层、Top-M=8/12/16，按层而非全局统一调整；这些不是保证有效的参数。预测得早但全错，或预测得准但来不及，都不能缩短关键路径。不要为了 CPU 预测而每层强制同步大隐藏状态，需测 CPU/GPU 放置预测器的净成本。

评价指标应包含：未驻留需求专家的预测召回率、预测精确率、及时完成率、浪费读取字节、额外淘汰量、真实 I/O 等待减少量和端到端 TPOT。缓存已有专家不应被混入“新预测成功”而抬高结果。

**9. CPU 辅助计算：先作为控制与调度资源，再有条件地执行专家。**

Fiddler 通过 CPU 执行部分专家减少独立 CPU/GPU 之间的权重搬运。GB10 的统一内存使这个收益条件发生变化，必须重新测量。KTransformers 的融合、任务调度与低算术强度专用内核值得借鉴，但论文中的 Intel AMX/AVX-512 优化不能直接搬到本机 Arm 核。[Fiddler](https://arxiv.org/abs/2402.07033)、[KTransformers](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)

CPU 首先负责 I/O 提交与完成、缓存维护、轻量预测及统计。基于本地大小核拓扑试验亲和性：后台维护可尝试小核，关键提交与小型计算可尝试大核；不要未经测试把所有 I/O 固定到小核，也不要直接启动 20 个专家计算线程。

专家计算需要比较三个条件：CPU 单独执行、GPU 单独执行、CPU/GPU 同时执行。按 dtype、每专家 token 数、线程数、驻留状态建立延迟表。对单 token BF16 专家，仅矩阵运算约 9.44 MFLOP、权重约 9 MiB，算术强度低，CPU/GPU 可能竞争同一 DRAM 带宽。

设 CPU 分担集合 C、GPU 执行集合 G，则选择应满足：

`max(T_GPU(G | C 并发), T_CPU(C | G 并发)) + 汇合与调度开销 < T_GPU(全部专家)`。

先试每层 Top-8 中 CPU 执行 0/1/2 个已驻留且预计很快完成的专家，再扩大搜索。输出必须等全部正式选中专家完成后按原 gate 权重汇合，不能把“未赶上截止时间”的专家丢弃。更换归约顺序可能带来浮点差异，需要验证数值误差和生成质量。

若权重仍在 SSD，CPU 同样需要等读盘；CPU 计算不能消除这部分 I/O。只有能缩短剩余计算关键路径或消除实际存在的拷贝时才可能获益。prefill 中专家 GEMM 更适合 GPU 的情况也应独立建模。

**10. Prefill 与 decode 使用不同策略，量化单独评估。**

Prefill 同时处理多个 token，选中专家的并集可能接近整层：应比较批量读取、按专家分组、权重复用与 microbatch 大小。避免每个 microbatch 都重新加载同一层的专家；也不要无限放大 microbatch 导致缓存溢出。Prefill 结束时按近期 prompt 的专家热度初始化 decode 缓存是可测候选，而不是默认保留全部 prefill 痕迹。

Decode 关注低延迟、小集合访问和跨 token 复用。除专家卸载外，可逐项评估 Flash Attention、KV 类型与容量、算子融合、GPU launch 开销，以及固定槽位后的 CUDA Graph 可用性。共享前缀 KV 复用主要帮助重复 prompt 的 TTFT，需要与专家缓存效果分开。

量化 BF16→Q8→Q4 可同时减少 SSD 字节和 DRAM 字节，并提高给定容量下的专家覆盖率；需核验本地 GB10 内核支持、实际块格式开销、反量化成本和任务质量，不能把 FP4 峰值算力换算为 decode 速度。BF16 到纯 4-bit 的权重位宽理论缩小四倍，但实际格式有 scale 等额外存储。

HOBBIT 提供了按专家重要性使用不同精度的方向。本项目应先做固定精度基线，再考虑动态精度，避免把量化收益归因于缓存或预取；动态精度也不属于严格保持 BF16 结果的优化。[HOBBIT](https://arxiv.org/abs/2411.01433)

投机解码可放在后期：验证多个候选 token 可能摊薄一次权重读取，但也会扩大专家并集和 KV 使用量。只有接受率和权重复用收益超过草稿、错分支与多余读取开销时才有效，不适合作为当前 I/O 路径尚未验证时的首项工作。

**11. 推荐实验顺序与停止条件。**

| 阶段 | 工作 | 判断是否继续的证据 |
|---|---|---|
| P0：可信基准 | 全驻留 GPU、mmap、当前 V2、CPU 专家基线；确认每种模式的真实算子位置 | 记录可复现命令、代码版本、驱动版本；冷 V2 有真实 miss/读取，热 V2 有可解释命中 |
| P1：硬件代价 | 实际专家大小的随机/顺序读、并发与队列深度；单专家 CPU/GPU 时间；内存复制 | 找出 SSD 带宽、提交开销、同步或计算谁占关键路径 |
| P2：低风险 I/O | 槽位复用、确定性三矩阵提前读、sidecar 对照、事件回收 | 等价输出下，读放大、复制流量或等待下降；若 SSD 已饱和，不继续靠加线程解释收益 |
| P3：缓存 | LRU、老化频率、分层配额、预取试用区；离线轨迹回放 | 同内存预算下，miss 字节或关键路径代价下降；用离线未来已知的缓存策略作分析上界 |
| P4：高层预取 | 历史预测、跨层、attention 前、训练预测器逐级添加 | 及时召回和 TPOT 同时改善；精确率高但 TPOT 不变时检查窗口和带宽 |
| P5：共享槽位直访 | 复制基线与紧凑槽位/指针表 | 命中场景首先受益，确认访存和地址转换没有抵消省掉的复制 |
| P6：CPU 协同 | 0/1/2 个专家分担、大小核亲和性和并发干扰 | 端到端 p50/p95 延迟下降；若增加 CPU 后 GPU 变慢且整体不收益，保持 GPU 计算 |
| 独立轴：量化 | BF16/Q8/Q4 与质量评估 | 每个精度单独列全驻留与卸载结果，形成延迟/容量/质量折中 |

缓存容量先扫 4/8/16/32 GiB，真正的总内存预算另行约束；prompt 可选 128/512/2048 tokens，生成至少 128/256 tokens，真实长上下文按开题目标追加。避免一开始执行全部笛卡尔组合，先单因素定位再组合最优候选。

每次记录 TTFT、prefill tokens/s、decode TPOT p50/p95、整段输出总 tokens/总耗时、峰值物理内存、需求与预测读取字节、cache 命中、过期预取、GPU 空闲时间、CPU/GPU 并发时的带宽与功耗/温度。不要只平均单 token 瞬时 tokens/s；使用多条真实文本，交错实验顺序，明确冷启动、应用热缓存、OS 热缓存与 SSD 实读条件。

系统优化先固定 token 轨迹和路由结果验证正确性，再做真实生成；预测器训练与评价请求分开。重复次数按方差决定，至少给出多次运行的分布。已有单 token 数据方差大，不能支持某个策略稳定快若干倍的判断。

**12. 可形成论文的具体问题。**

推荐题目方向：“统一内存架构下，面向 SSD 卸载的 MoE 专家驻留与预取协同优化”。候选贡献分别是：以关键路径等待代价分配层间缓存；受带宽、队列和截止时间约束的多层预取；消除统一 DRAM 中重复副本并控制 CPU/GPU 竞争的执行策略。

这些是研究假设而非新颖性声明。缓存、预测预取和 CPU/GPU 协作已有大量工作；贡献需要通过 GB10 上的可复现测量、与已有策略的消融对照，以及统一内存约束下不同于独立显存设备的机制证据来建立。拿到开题报告后，再据其研究范围、模型选择和时间安排收敛为两到三个重点。

后续针对毕业论文的新颖性复核发现，SeqMoE、HybriMoE、FIRM-MoE 等已有工作进一步覆盖了上述部分候选方向。因此，本文件中的工程路线不能直接当作论文创新声明。更具体的差异化设计、最近相关工作和验证门槛见 [毕业论文候选方案与新颖性分析](/home/cuichengshang/moe_offload/docs/gb10-moe-thesis-directions.zh.md)。
