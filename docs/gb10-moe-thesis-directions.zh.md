本文针对“已有优化是否足够支撑毕业论文”给出候选研究方案。检索日期为 2026-09-23，暂按硕士论文的研究深度设计；具体学位要求和开题报告尚未提供。下面的差异化设计均是需要验证的研究假设，未完成系统性查新，也没有新的性能实测，不能据此宣称首次提出或保证论文通过。

**判断：实现 O_DIRECT、LRU、多线程读取和跨层预取，可以形成良好的实验平台，但把已有机制相加，通常不足以说明独立的研究贡献。**

更有说服力的路径是：发现既有策略在本机上的明确失效条件，建立能够解释该条件的模型，提出针对性决策方法，并在相同预算和输出要求下，通过强基线与消融验证。设备名称变化、增加模块数量、把简单评分称为智能调度，都不能替代这个过程。

**已有工作已经覆盖到什么程度。**

| 常见提法 | 已有直接相关工作 | 对选题的影响 |
|---|---|---|
| 动态分配 CPU/GPU 专家、跨层预取和缓存打分 | [HybriMoE](https://arxiv.org/abs/2504.05897) | 需要明确本方法如何建模统一 DRAM 的并发干扰 |
| 预测未来多层、截止时间调度、预测驱动淘汰、CUDA Graph 兼容 | [SeqMoE](https://arxiv.org/abs/2609.12978)，2026-09 预印本 | 上一版提出的宽泛组合已有高度相近的工作，必须继续收窄 |
| SSD 读取、存储层次、CPU/GPU 混合执行 | [SSD-LLaMA](https://arxiv.org/abs/2609.18110)，2026-09 预印本 | SSD 卸载框架本身不能作为主要新颖性来源 |
| 专家拆成可独立加载部分、资源自适应预取 | [FIRM-MoE](https://ojs.aaai.org/index.php/AAAI/article/view/39106) | 不能笼统声称首次细粒度加载；其正文将 gate/up/down 矩阵作为独立子模块 |
| 结合近期性和频率学习 SSD 专家缓存策略 | [FlashMoE](https://arxiv.org/abs/2601.17063) | 学习型 LFU/LRU 混合也不是充分差异 |
| Top-K 共激活关系影响缓存与延迟 | [SlimCaching](https://arxiv.org/abs/2507.06567) | 专家集合感知已有理论先例，需区分分布式放置与本机在线 I/O |
| 无损压缩与缓存调度协同 | [ZipMoE：On-Device Serving](https://arxiv.org/abs/2601.21198) | 压缩权重加缓存只能作为对照或进一步细化的方向 |
| 专家与 KV 的动态内存划分 | [VAMP](https://arxiv.org/abs/2609.13537)，2026-09 预印本 | 动态 KV/专家容量本身已有研究，不适合直接作为新点 |

上表是选题筛查，不是对这些论文全部实现细节的复现核验。预印本的性能结论仍是作者报告；本方案不沿用其中的加速倍数。

**方案 A：以整组 Top-K 的完成时间为目标，联合决定缓存与读取顺序。**

研究问题：两个策略的专家命中率相同，为什么其中一个仍有更多长停顿？在一层需要全部 Top-K 专家输出的条件下，最后一个未就绪专家可能决定整层完成时间。单专家命中数未必足以表示这个代价。

设计：从真实轨迹收集每层 Top-K 集合、每个专家的驻留/读取状态和读取完成时间。缓存替换与预取决策不仅估计单专家概率，还估计高概率专家组合能否按时完成。在线优先服务对当前或近期层的最后完成时刻最有影响的请求，同时限制错误预测对队列和空间的占用。

在当前“等待本组选中权重就绪后计算”的执行方式下，可用 `W_l = max(0, max_e F_l,e - D_l)` 估计该层暴露的加载等待，F 是读取完成时间，D 是不考虑本层权重等待时的需求时间。引入边读边算后，应改成完整计算依赖图的完成时间，而不能继续直接套用这个屏障模型。

优化目标可采用 `平均 TPOT + λ × 尾部风险`，尾部风险使用 p95 或 CVaR 等统计量。Top-K 专家之间存在依赖，不能未经验证就把各专家概率相乘，也不能宣称普通贪心算法有理论保证。

最小原型：不改预测器，只在相同预测结果、相同缓存预算下，更换入场/淘汰和队列排序规则。候选淘汰集可限制为近期低价值项，避免在线组合枚举。

验证：报告字节命中率、整组及时就绪率、p50/p95 TPOT、慢请求来源和决策开销。对比独立热度策略、按缺失字节代价策略、截止时间优先策略。反例与真实轨迹都要包含；若真实 SSD 延迟和关键路径差异很小，集合目标可能没有可利用空间，应降级。

差异边界：共激活缓存已由 SlimCaching 等研究；本候选的拟研究差异是单 NVMe 的相关排队延迟、在途读取状态与在线整层尾延迟目标。只有进一步查新和实验支持后，才能将该差异写为贡献。

**方案 B：依据 SSD 状态自适应选择专家内部计算块，实现精度不变的流式执行。**

研究问题：整专家加载单位太大时，是否可以更早启动有用计算并缩小活动工作集，而不会被更多 kernel 启动与小请求开销抵消？

以 SwiGLU 专家为例，`y = W_down [SiLU(W_gate x) ⊙ (W_up x)]`。把中间维划分为互不相交的块 J_b，可以写成：

`y = Σ_b W_down[:, J_b] [SiLU(W_gate[J_b, :] x) ⊙ (W_up[J_b, :] x)]`。

它在实数算术下等价，所有块都必须参与；浮点累加顺序变化可能产生数值差异。它不是跳过神经元，也不自动减少权重总字节。

本地专家中间维为 768，BF16 完整专家 9 MiB。按 128 维分成 6 块，每块对应三矩阵切片共约 1.5 MiB。存储布局按块打包匹配的 gate/up 行和 down 列；双缓冲执行读取下一块、计算当前块、回收上一块。

创新候选应放在自适应选择：根据缓存命中、SSD 有效带宽、队列尾延迟、GPU kernel 尺寸效率与共享 DRAM 干扰，在完整专家、矩阵级、64/128/256 维块之间选择。热专家继续使用高效完整内核；冷专家才进入流式路径。量化版本还需保持量化块与 scale 的合法边界，初版只验证 BF16。

最小原型：先实现单专家离线重排和双缓冲执行，验证误差与不同块宽的真实延迟，再扩展至 Top-K 和跨层。选择规则先用小型测量表，不必引入强化学习。

对照必须包含完整专家、FIRM-MoE 式矩阵级调度和最佳固定块宽，不能只对比串行整读。若 3 MiB/9 MiB 请求已经充分利用 SSD，细分导致吞吐和内核效率下降，应允许自动回到整专家路径。

差异边界：专家细粒度拆分已有大量研究。FIRM-MoE 正文把三个矩阵作为可独立加载子模块，本方案进一步考虑中间维配对切片、输出部分和累加与 NVMe 服务时间联合决定块宽；仍需检索其他子矩阵流水研究，不能声称首次分块。[FIRM-MoE 正文](https://ojs.aaai.org/index.php/AAAI/article/download/39106/43068)

**方案 C：联合划分热点驻留与在途缓冲空间，避免缓存越大反而越慢。**

研究问题：总内存固定时，扩大已驻留专家容量，可能挤压为后续层读取保留的槽位，迫使当前计算结束后才能读入下一批权重。减少 miss 与增加重叠窗口之间是否存在可测的最优点？

设计：统一槽位池采用 FREE、LOADING、READY、IN_USE 状态，引用和事件控制回收。物理页只统计一次，不能把“缓存副本”和“工作区别名”重复计入。固定 KV/非专家权重预算后，动态控制热点保护额度、在途读取额度、预取数量和需求预留槽位。

每次增加预取空间会造成缓存驱逐；因此控制器比较“增加一份驻留容量减少的未来缺失时间”和“增加一份在途容量减少的当前流水停顿”。使用短窗口统计、迟滞与最小调整间隔，避免反复驱逐和装入同一专家。

`在途字节约等于带宽 × 服务时间` 只能作队列容量的数量级参考，SSD 服务时间本身随并发变化，还需包括计算使用中的不可回收槽位，不能据此直接给出全局最优容量。

最小原型：先保持 GPU 计算与现有专家粒度不变，扫描固定划分，证明两个极端都不理想；再实现小步动态控制，与最优固定划分和静态双缓冲比较。未出现明显权衡时，动态控制可能不值得做。

验证：相同整机物理预算下，记录缺失字节、等待空槽时间、读取重叠率、临时峰值内存、TPOT。零拷贝池、事件回收和控制算法分别消融，不能把删除重复复制的收益全归因于控制器。

差异边界：动态内存分配和缓存/预取协同是已有思想。拟研究对象是统一物理池中驻留、正在读取和正在计算三类用途的联合决策，而非把 GPU 显存划给 CPU 内存。VAMP 的专家/KV 划分可作为相关工作，但不是完全相同的问题。

**方案 D：显式估计共享内存干扰的 CPU/GPU 专家调度。**

研究问题：CPU 单独测量很快，并不意味着加入 CPU 后整体更快。GPU 与 CPU 同时执行带宽受限算子时，共享 DRAM 竞争可能抵消并行收益。

设计：建立条件延迟表，输入为每专家 token 数、dtype、CPU 线程数及核类型、GPU 阶段、读取/解压并发度。预测 `T_GPU(G | C 并发)` 与 `T_CPU(C | G 并发)`，而不是把两个独立吞吐量相加。枚举少量 CPU 分担数量，例如 0/1/2 个专家，选择最大完成时间加汇合成本最小的方案。

CPU 空闲本身不是分配任务的理由；只有减少系统总完成时间才分担。GPU 已接近 DRAM 带宽上限时，可以主动限制 CPU 专家线程，把 CPU 留给 I/O 与控制。权重在 SSD 时，两侧仍需要读取，不把 CPU 计算当作消除 SSD 缺失的方法。

最小原型：单层 Top-8，GPU-only、CPU-only、固定混合、不考虑干扰的动态混合、考虑干扰的动态混合五组。先用日志拟合模型，随后在线低频修正；保留 GPU-only 回退。比较在不同上下文、缓存命中率、CPU 线程数下的模型误差和端到端收益。

差异边界：HybriMoE 已研究动态层内分配与缓存协同；Hydrogen 也研究过异构共享内存干扰。潜在贡献在 SSD 加载、Arm 大小核与 GB10 内存竞争耦合下的可验证代价模型与控制规则，不是首次考虑 CPU/GPU 并行。[HybriMoE](https://arxiv.org/abs/2504.05897)、[Hydrogen](https://people.iiis.tsinghua.edu.cn/~gaomy/pubs/hydrogen.sc24.pdf)

**方案 E：面向任务切换的预取风险控制，与预测器解耦。**

研究问题：固定 Top-M 预取在同主题文本上可能有效，在代码、自然语言和工具结果切换后可能持续错读。平均召回率掩盖了短时间内的带宽浪费和缓存污染。

设计：保留原预测器，在线监测概率校准误差、近期漏预测、无用读取字节和缓存热度变化。状态稳定时增加预取范围；检测到分布变化时缩小预测窗口、降低旧频率权重、保护真实需求槽位。用“额外读取预算”和“需求延迟预算”约束动作，增加迟滞避免抖动。

最小原型：跨层 gate 或上一 token 历史预测器均可，不需要先训练大预测网络。离线用独立请求校准，在线每隔若干 token 更新阈值。检验静态主题、混合主题、长工具输出和请求边界，报告切换后的恢复 token 数、错预取字节与 p95 延迟。

差异边界：SPICE 已有置信度感知前瞻，FIRM-MoE 已有自适应预取。拟研究差异是分布变化期间的有界投机预算及恢复过程，不是首次根据置信度调整 Top-M。不能在任意分布变化下声称校准或风险界仍严格成立。[SPICE](https://arxiv.org/abs/2608.21240)

**方案 F：面向单 NVMe 的访问布局与在线读取范围联合优化。**

研究问题：哪些专家应该相邻存储，以及为了合并读取多读多少无用字节才划算？

设计：用训练轨迹建立同层专家共激活图或超图，生成保持专家身份不变的 sidecar 排列；在线根据已缓存区间、缺失区间、队列深度和截止时间，选择多次离散读取或包含间隙的一次范围读取。比较目标应包含完成时间和读放大，不能只最小化请求数。

最小原型：不改计算 kernel，先做 sidecar 索引和轨迹重放。对比原 GGUF、简单整专家打包、随机排列、共激活排列，以及有/无读取合并。训练与测试任务分开，验证访问关系是否跨任务稳定。

适用限制：本机只有一个 NVMe，且 BF16 专家很大，SSD 随机大读和顺序大读差距可能有限；低比特或方案 B 的小块场景可能更有价值。没有可测带宽或尾延迟差异就降级为工程优化。

**方案 G：压缩态与可执行态专家的动态选择，同时计算解压干扰。**

研究问题：统一内存中保留较多压缩专家是否比保留较少可直接计算专家更快？答案取决于压缩比、复用间隔、解压速度及其对 GPU 的干扰。

设计：热专家保留可执行表示，温专家保留无损压缩表示，冷专家在 SSD。控制器比较保留原表示、保留压缩表示与淘汰的预期未来代价；转码和重新解压有迟滞。两种表示是同一物理池中的逻辑状态，总容量必须统一核算。

最小原型：先抽样不同层/专家，测真实压缩率与并发解压吞吐。对 SSD 冷读，检查 `压缩后读取时间 + 解压时间 + 干扰成本 < 原始读取时间`；对压缩态内存命中，比较解压与重新从 SSD 读的代价。无收益则不推进完整系统。

差异边界：ZipMoE 已研究无损压缩与缓存调度，因此本方向不能直接作为新点。只有共享带宽下双表示入场、保留和解压位置选择存在明显未解决问题时，才考虑深入。BF16 和已量化权重的压缩空间不同，不承诺固定压缩比。[ZipMoE](https://arxiv.org/abs/2601.21198)

**方案 H：按新增 SSD 字节选择 microbatch，减少多请求之间的重复专家读取。**

研究问题：增加 batch 既可能提高权重复用，也可能激活几乎全部专家并挤爆缓存。固定 batch 大小难以适应内存受限的 SSD 卸载。

设计：对并发请求，根据预测专家集合估计加入某请求后新增的缺失字节，并同时约束最长等待时间、KV 和工作区容量。相同专家需求尽量放在同一 microbatch，加入等待时长奖励防止冷门请求饥饿；不改变单个请求内部的 token 顺序。

实际专家在执行 router 后才确定，组批时必须使用可用历史或预测，不能用未来真实路由制造结果。先做固定轨迹下的离线收益上界，再实现在线近似。报告 tokens/s、TTFT、TPOT p95、公平性和额外排队时间。

差异边界：专家感知组批、缓存亲和调度均有相关工作，MoE-Lightning 与 ZipMoE 是必要对照。拟研究差异是单 NVMe 缺失字节和内存峰值共同约束的组批。需要多请求运行时，当前单请求卸载原型改造较大，不列首选。[MoE-Lightning](https://pschafhalter.com/papers/2025-asplos-moe-lightning.pdf)

**如何选择，不建议把八项全部实现。**

| 路线 | 核心组合 | 适合条件 | 最大风险 |
|---|---|---|---|
| 缓存与调度主线 | A + C，E 作为增强 | 希望优先复用当前代码、较少修改 CUDA 内核 | 与既有缓存/预测工作接近，需要清晰的因果证据 |
| SSD 流式执行主线 | B + C，F 作为补充 | 愿意做权重布局和 CUDA kernel/算子改造 | 分块后内核效率和 SSD 吞吐可能下降 |
| 异构协同主线 | D + C，必要时加入 E | 对 CPU 向量化、测量与资源控制有经验 | CPU/GPU 并发收益可能很小，甚至持续为负 |

按当前代码基础，优先建议 A+C。若希望论文更突出底层机制，并且有足够 kernel 开发时间，先用单专家实验筛查 B+C。两条路线均可暂用题目“面向统一内存平台的 MoE 大模型 SSD 卸载与关键路径优化”，等实验确定后再收窄题目。

建议采用“两个算法或机制贡献 + 一套验证平台”的结构。平台贡献负责正确读取、可复现日志、真实工作负载和预算核算；它支撑研究，但不应包装成第三个算法创新。先写拟验证问题，实验结束后再将成立的部分写成实际贡献。

**立项前应通过的可行性门槛。**

先做四类短实验：固定总预算下扫描驻留/在途空间；同等命中率下检查整层等待是否显著不同；比较整专家/矩阵级/中间维块的读取与执行；测 CPU/GPU 并发是否改变对方延迟。这些实验直接决定 A/B/C/D 中哪两项有研究空间。

离线缓存回放只能筛查思路。回放必须保留每层 Top-K 集合、缓存固定期间的语义和在途状态，不能把同一 Top-K 内专家串行展开后允许错误的组内淘汰，也不能用测试集未来信息指导在线策略。最终要返回真实端到端执行验证。关于评估陷阱，可参考 [Reproducible Evaluation of MoE Expert Caching](https://arxiv.org/abs/2608.07911)。

实验至少区分全驻留、工作集能放入预算、持续超预算三种运行区域。当前 30B BF16 可放入设备物理内存，受限预算实验需要明确声明；若只限制应用缓存而让 OS page cache 保存全部模型，不能声称测到了真实 SSD 卸载效果。

控制相同权重精度、总内存预算、请求与 token 序列、冷热状态和运行时。至少比较 LRU、老化频率策略、成本感知策略以及最相关论文的可用实现或忠实适配；仅超越朴素 LRU 不足以证明超越已有工作。第二种模型/专家形状需要实际兼容实现，不能只凭同一模型的多份 prompt 宣称模型泛化。

消融应分别关闭集合目标、动态空间划分、并发干扰模型和漂移控制，并报告控制器时间。对修改浮点归约次序的方案，报告输出误差与任务质量；对纯缓存与读取策略，正式 router 和完整专家执行保持一致。

评价重点是贡献是否有明确适用条件和稳定收益，而不是先承诺某个加速倍数。若某方向的改进只出现在特制轨迹或几乎不会遇到的参数范围，就应缩小结论或更换方向。
